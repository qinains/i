# 浏览器会话存储基准

先构建浏览器应用并安装 Chromium，再运行基准：

```sh
npm ci --prefix web
sh scripts/build_web.sh
npm exec --prefix web -- playwright install chromium
node web/bench-session-storage.mjs
```

脚本启动随机端口的本地静态服务器，使用一次性 Chromium 上下文和合成记录，不读取真实浏览器配置、不调用模型。默认每组启动 5 次、每次保存 7 次。可用 `BENCH_RUNS=10` 增加样本。

- 冷启动：从导航到应用报告 `Ready`，禁用 Service Worker，使用新上下文。
- 内存：采样 Chromium 的 JavaScript 堆峰值，不包括总 RSS、WASM 或 Blob 开销。
- 保存：克隆、校验、序列化和 IndexedDB 提交耗时，不含输入防抖。

## 对照结果

macOS ARM64，Chromium 156；每组 5 次启动、35 次保存。箭头两端分别表示超长消息预览改动前后。

| 合成数据 | 启动中位数 | JS 堆采样最高值 | 保存中位数 |
| --- | ---: | ---: | ---: |
| 1 个小会话，约 256 KiB | 115 → 129 ms | 3.8 → 3.8 MiB | 0.9 → 1.5 ms |
| 100 个小会话，约 25 MiB | 139 → 166 ms | 40.1 → 40.1 MiB | 0.8 → 1.2 ms |
| 4 MiB 历史，界面只显示短消息 | 95 → 125 ms | 11.3 → 11.3 MiB | 11.0 → 14.8 ms |
| 同一 4 MiB 历史，另有一条 4 MiB 无换行消息 | 20.78 s → 122 ms | 15.3 → 15.4 MiB | 27.2 → 27.6 ms |

对照显示，最大的停顿来自把一条超长消息放进页面，而不是仅仅读取长历史。页面现在只渲染单条超长消息的前约 16 Ki 个 UTF-16 代码单元，可下载原文；保存记录和模型历史不变。大记录保存仍需要整体写入，在这个样本中没有明显加速。

这些是单机、合成输入下的诊断结果，不是性能承诺。暂不迁移 IndexedDB 表结构；如果移动端实测显示大批会话恢复内存过高，先评估按需加载会话历史。如果真实长会话保存延迟超出预算，再评估把草稿与历史拆开存储。
